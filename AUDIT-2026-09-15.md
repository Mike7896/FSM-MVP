# MVP functionality audit — September 15, 2026

## Summary

The repository has substantial real infrastructure and database-backed screens, but the primary customer journey stops after sending and viewing a quote. Customer approval, customer signing, invoice delivery, and customer payment are not connected into an end-to-end workflow. Several other screens look usable but cannot persist their inputs.

This was a source-code audit of pages, components, API handlers, document operations, queries, schemas, migrations, and integration modules. Findings below distinguish missing UI wiring from missing backend behavior. External services and a deployed database were not exercised; existing implementations are not thereby certified to work in production. No application code was changed.

## Highest-priority workflow gaps

### 1. Customers cannot approve quotes or select extras

- `components/quote/projection.tsx:229` renders “Approve this quote” / “Approve & pay … deposit” as a styled `div`, without an event handler.
- Optional items are also plain rows, despite “Tap to add — your total updates” at line 214.
- `app/share/[token]/page.tsx` renders that same component directly.
- `lib/documents/operations/accept-quote.ts:48` implements acceptance and contract generation, but its callers are verification scripts, not application routes or actions.

**Impact:** sending a quote is implemented, but a customer cannot progress it into an accepted agreement. This also blocks the ordinary path into contracts, deposits, and subsequent work.

**Needed:** a token-authorized acceptance endpoint, interactive customer controls, selection persistence and pricing validation, and the transition into signing/deposit billing.

### 2. Customer contract signing is not connected

- `lib/queries/share.ts:87` rejects every document type except `quote`. Contract, change-order, and invoice share links therefore cannot render through the shared page.
- `lib/signing/sign.ts` contains real signature validation, recording, and audit fields.
- The only signing route, `app/api/v1/documents/[id]/sign/route.ts`, requires an authenticated organization owner/admin. There is no share-token signing route.
- Separately, that account route accepts `party: "customer"` from the request body (lines 24 and 53). It does not enforce that an account-authenticated business signer is signing only as the contractor.

**Impact:** customers cannot complete the intended signature flow. The account signing route also needs a clear, enforced signer-role boundary before customer signing is exposed.

### 3. “Send this bill” creates an invoice but does not deliver it

- `components/invoice-editor.tsx:95` posts to the invoice API with `issue: true` and navigates to the invoice detail page.
- `lib/documents/operations/create-invoice.ts:160` saves the document, invoice details, and phase/evidence associations. It does not create a share link or send an email.
- The detail page consequently says the invoice has not been sent when there is no token. Existing invoice tokens would encounter the quote-only resolver described above.
- `app/api/share/[token]/pay/route.ts` implements Stripe PaymentIntent creation, but no customer payment UI calls it.

**Impact:** the business can create issued invoices in its records, but cannot send a payable bill through this workflow. Stripe infrastructure alone does not complete collection.

### 4. Change orders cannot be saved or sent

- `app/(app)/jobs/[id]/change-orders/new/page.tsx:95` supplies `autosave={false}` to the editor and no preview callback.
- `components/quote-editor/index.tsx:207` only saves when autosave is enabled and invokes an optional preview callback; this page supplies neither effective path.
- There is no change-order API. `lib/documents/operations/index.ts:23` explicitly marks creation and invoicing operations pending.

**Impact:** entering additional work produces only an in-memory draft. Leaving the page loses it. Existing tables and read-side agreement calculations do not provide an authoring workflow.

## Settings that do not represent working systems

### 5. Subscription cancellation uses dummy account facts and cannot cancel

`app/(app)/account/billing/cancel/page.tsx:23` hardcodes **“2 open jobs,” “Sep 3,” and “3 a month.”** These are not read from the account. Its cancellation button at line 95 has no handler.

The Stripe Billing Portal integration exists elsewhere, so a working integration can be reused. The dedicated cancellation screen needs actual subscription/job data and a real cancellation action. Its export promise also depends on the missing export system below.

### 6. Automations and notification preferences are presentation only

- `components/office/automations-panel.tsx` uses local React state for send modes and uncontrolled switches for other settings. Reloading loses choices.
- `components/settings/notification-table.tsx` uses hardcoded `defaultChecked` values without persistence.
- No preference API or automation execution system was found. The configured cron drains connector sync jobs; it does not run reminders, quiet hours, or notification delivery.
- The quote follow-up component can perform a manually triggered resend. That is distinct from scheduled automated follow-up.

**Impact:** “Sends itself,” quiet hours, notification channel choices, and “Always” payment receipts imply behavior the application has not implemented.

### 7. Data import, export, and accountant handoff are placeholders

All three actions in `app/(app)/office/data/page.tsx` are unwired buttons. No corresponding import/export/packet API was found. The cancellation screen links here as though export is available.

## Incomplete backend modules and product claims

### 8. QuickBooks connects, but cannot sync business records

`lib/connectors/quickbooks/adapter.ts` implements OAuth; queue, credential storage, retries, and cron infrastructure exist. However, all five entity push functions in `lib/connectors/quickbooks/push.ts:69` throw “isn't built yet.” No application business operation calls `enqueue`; only the connector verification script does.

The registry nevertheless describes QuickBooks as available and promises customer/invoice/payment synchronization. Completing this requires both entity mappers and event producers, not merely credentials.

### 9. Bank and Square connectors are advertised ahead of implementation

`lib/connectors/registry.ts` marks Plaid and Square available. `lib/connectors/index.ts:16` registers only the QuickBooks OAuth adapter; Stripe Connect has its own implemented hosted path. The connection-start route returns `not-ready` when an adapter is missing. No Plaid Link flow or bank transaction matching implementation was found. PayPal and Gmail are explicitly planned.

### 10. Trade packs have purchase/enablement scaffolding, not the advertised contents

`lib/packs/catalog.ts:70` advertises Electrical with 24 job types and 11 quote templates, but supplies descriptive catalog metadata rather than those template definitions. Preset/assembly tables exist without a corresponding library CRUD/use workflow. Inline scope-tree assemblies are implemented and are a different capability.

`app/(app)/office/packs/[pack]/configure/page.tsx:90` has unwired Save/Later buttons and the same fixed electrical rate fields for every pack. The pack API persists enablement only. Trade-specific contents, configurable rates, and their application to new quotes need implementation.

### 11. Price Book and AI drafting are deferred features

`app/(app)/price-book/page.tsx:25` always renders the same “Still learning your numbers” screen. It does not query pricing history or learn rates.

`lib/quote/seed.ts:33` parses a typed sentence into customer/title only; it does not generate scope or prices. Its comment explicitly reserves AI drafting for a future implementation. Neither ordinary demo mode nor this parser should be counted as hidden fake business data: demo records are labelled, and sentence-seeded drafts start empty.

### 12. Document lifecycle composition remains incomplete

`lib/documents/operations/index.ts:20` lists automatic deposit issuance, dedicated draw issuance, final settlement, change-order creation/invoicing, and quote revision as pending. Generic invoice creation covers part of deposit/draw/final billing, but does not orchestrate acceptance → deposit → customer payment or final reconciliation.

The final-balance editor starts at zero unless a phase supplies an amount (`components/invoice-editor.tsx:77`); it does not calculate a final settlement amount for the contractor. A coherent revision workflow is also absent even though quotes can be saved or duplicated.

### 13. Billing limits are not enforced consistently on draft updates

`createInvoice` checks cumulative billing against the agreement, but `lib/documents/operations/update-invoice.ts:72` allows a draft amount to change and be issued without repeating that check. A draft initially created within the limit can therefore be increased beyond it through the API. The create-time aggregate check also occurs before its transaction; concurrent non-phase invoices need further concurrency validation.

This is a source-confirmed missing update validation plus a concurrency risk, not a claim that an overbilling incident was reproduced against a live database.

## What already has real implementation

- Database-backed dashboard, quote/job/customer/invoice lists, and financial aggregations.
- Quote creation, scope editing, persistence, duplication, email/link sending, and view tracking.
- Organization identity, document branding, defaults, and license management.
- Phase planning and completion evidence, plus capture upload and note intake.
- Document storage, freeze rules, signature primitives, and ledger recording/reversal.
- Authentication, Stripe subscription/portal integration, and Stripe Connect server/webhook plumbing.

These are valuable foundations. Their existence does not resolve the missing customer-facing transitions identified above.

## Validation and limits

- `npm run typecheck`: passed.
- `npm run quote:check`: all checks passed. The runner initially encountered a sandbox process-start restriction; the permitted rerun succeeded.
- `npm run lint`: zero errors, one unused-variable warning in `components/documents/document-thumbnail.tsx:49`.
- No database-mutating integration scripts, external sends, real payments, or deployment checks were run.
- Existing uncommitted work was left intact. This report is the only intentionally added file.

## Suggested implementation order

1. Complete one real customer journey: send quote → accept → sign → receive/pay deposit invoice → ledger update.
2. Deliver and collect milestone/final invoices; enforce invoice limits consistently; add manual payment recording.
3. Complete job/customer maintenance, standalone creation, and change orders.
4. Add receipt entry and inspection scheduling/results.
5. Make cancellation work and replace false account facts; persist settings and either implement or clearly label deferred automation/integration features.
6. Build packs, price history, import/export, and further integrations according to the intended MVP scope.
